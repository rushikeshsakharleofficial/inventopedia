# M2 Security Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Complete M2 authentication and multi-tenant security only.

**Architecture:** Extend JWT middleware with user-scoped membership lookups and
explicit role guards. Harden existing tenant RLS using private, caller-bound
security-definer helpers and a forward migration.

**Tech Stack:** Hono 4, TypeScript strict, Zod 3, Supabase PostgreSQL, Vitest.

**Spec:** docs/superpowers/specs/2026-11-01-m2-security-design.md

## Global Constraints

- Keep the existing error envelope and use Zod for request/response validation.
- All DB changes through versioned migrations; retain RLS on tenant tables.
- No M3 CRUD/quota APIs, paid infrastructure, deployment, or frontend expansion.
- Preserve existing working-tree changes; one writer; work on feat/m2-security.

## Review Focus

- Malformed or expired JWT: 401 without tenant queries.
- Database failure: 500 envelope, never disguised as missing membership or 401.
- Stale project membership after org removal: no project access.
- Valid project under the wrong org: 404 without leaking tenant information.
- Direct DB writes/RPC: cannot escalate roles, move tenants, or impersonate users.
