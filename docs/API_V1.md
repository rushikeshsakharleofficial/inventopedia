# API v1 Contracts — Inventopedia

Base path: `/api/v1`

## Common

### Headers
- `Authorization: Bearer <supabase_jwt>` (all authenticated endpoints)
- `X-Request-Id: <uuid>` (generated by middleware if absent)

### Error Response
```json
{
  "error": "Human-readable message",
  "code": "ERROR_CODE",
  "requestId": "uuid"
}
```

### Pagination
Server-side cursor pagination:
```
?cursor=<opaque>&limit=<1-100>
```
Response:
```json
{
  "data": [...],
  "pagination": { "cursor": "next_cursor_or_null", "hasMore": true }
}
```

## Endpoints

### Health
| Method | Path | Auth | Description |
|--------|------|------|-------------|
| GET | `/api/v1/health` | No | Health check |

### Organisations

| Method | Path | Access | Description |
|--------|------|--------|-------------|
| POST | `/api/v1/organisations` | Signed in | Create org with caller as owner |
| GET | `/api/v1/organisations` | Signed in | List caller's orgs and roles |
| GET | `/api/v1/organisations/:orgId` | Org member | Get org and caller role |
| GET | `/api/v1/organisations/:orgId/members` | Org member | List org memberships |

Creation body: `{ "name": "Example", "slug": "example-org" }`. Name length is
1–200; slug length is 3–64, lowercase letters/digits/hyphens, with alphanumeric
first and last characters. Successful responses use `{ data, requestId }`;
creation returns 201, reads return 200. Duplicate slug returns 409 / `SLUG_CONFLICT`.

Clients sign in with Supabase Auth and supply its access token. The API validates
tokens with Supabase `getUser`; it does not accept client-supplied user IDs or roles.
Invalid/missing credentials return 401 / `UNAUTHORIZED`. Scoped org/project IDs
must be UUIDs (400 / `VALIDATION_ERROR`). Invisible or inaccessible scope returns
404 / `NOT_FOUND`, insufficient role returns 403 / `FORBIDDEN`, and database or
unexpected failures return 500 / `INTERNAL_ERROR`. All use the common error format.

### Tenant scope middleware

Use `authMiddleware()` before `orgScope()` / `projectScope()`. Scope IDs come
from `:orgId` / `:projectId` route parameters. A nested org and project must agree.
Follow with `requireOrgRole(...allowed)` or `requireProjectRole(...allowed)` for
operations requiring elevated permissions; guards deny access without scope.
Org roles: owner, admin, member. Project roles: owner, admin, editor, viewer.
Owner/admin org roles inherit corresponding project roles; other users require
both org and explicit project membership. Guards use explicit allowed-role lists.

### Projects (M3)

All paths below begin with `/api/v1/organisations/:orgId` and require a valid JWT.

| Method | Suffix | Access | Response |
|--------|--------|--------|----------|
| POST | `/projects` | Org owner/admin | 201, created project |
| GET | `/projects` | Org member; RLS filters visible projects | 200, paginated projects |
| GET | `/projects/:projectId` | Project member or org owner/admin | 200, project |
| PATCH | `/projects/:projectId` | Project owner/admin or org owner/admin | 200, updated project |
| DELETE | `/projects/:projectId` | Org owner only | 200, `{ data: { id }, requestId }` |
| GET | `/subscription` | Org owner/admin | 200, subscription usage |

Creation accepts `{ name, description? }`. Name is trimmed, 1–200 characters;
description is nullable and at most 2000 characters. PATCH accepts those same
fields with at least one present; `{ description: null }` clears the description.
Unknown fields, including actor, role and tenant IDs in the body, are rejected.
The server derives the actor from the validated JWT. Project objects contain
`id`, `orgId`, `name`, `description`, `createdAt`, and `updatedAt`.

Listing accepts `limit` (integer 1–100, default 20) and the opaque `cursor` returned
by the preceding page. Projects are ordered by immutable UUID ascending, not by
creation time. Responses contain `{ data, pagination: { cursor, hasMore }, requestId }`;
the terminal cursor is null. Invalid cursors/query values return 400. Concurrent
inserts with IDs before the cursor are only visible on a fresh listing.

Creation enforces the organisation limit transactionally: Free 2, Starter 5,
Business 10, Enterprise configured custom limit (null means unlimited). A full
quota returns 409 / `PROJECT_QUOTA_EXCEEDED`. Missing subscription configuration
and unexpected database errors return 500 / `INTERNAL_ERROR`. Creation inserts
the creator's owner membership and audit event in the same transaction.
Deletion physically removes an empty project and cascades its project memberships.
M4 inventory rows restrict project deletion: a project containing retained inventory
returns 409 / `PROJECT_NOT_EMPTY`. Both PostgreSQL restrict (`23001`) and foreign-key
(`23503`) conflicts use this envelope without exposing private constraint details.
Category, template, item and stock endpoints are implemented locally through M8.

Subscription usage response:

```json
{
  "data": { "tier": "free", "maxProjects": 2, "projectsUsed": 1, "projectsRemaining": 1 },
  "requestId": "uuid"
}
```

Usage counts all projects in the organisation; remaining capacity is clamped to
zero if a downgrade leaves usage above the limit. Unlimited Enterprise returns
null for both `maxProjects` and `projectsRemaining`. This read is informational;
creation performs its own locked quota check. There are no subscription-write,
billing or project-membership management endpoints in M3. Frontend auth UI remains deferred.

### Categories (M5)

Base: `/api/v1/organisations/:orgId/projects/:projectId/categories`.
All routes require a valid JWT and matching org/project membership.

| Method | Suffix | Access | Response |
|--------|--------|--------|----------|
| POST | `/` | Project owner/admin | 201, created category |
| GET | `/` | Project member | 200, paginated categories |
| GET | `/:categoryId` | Project member | 200, category |
| PATCH | `/:categoryId` | Project owner/admin | 200, updated category |
| DELETE | `/:categoryId` | Project owner/admin | 200, `{ data: { id }, requestId }` |

Org owner/admin inherit corresponding project permissions. Editors/viewers can read
categories but cannot write. Every query uses the caller JWT, `inventory` schema
and explicit project filter. Neither path parameters nor request bodies can grant
access to another organisation or sibling project.

Creation body: `{ "name": "Tools", "parentId": null, "sortOrder": 0 }`.
Only name is required; parent defaults null and sort order defaults 0. Names are
trimmed and must contain 1–200 characters. Sort order is an integer from
-2147483648 through 2147483647. Parent IDs must be UUIDs in the current project.
PATCH accepts those same fields, at least one present; omitted fields stay unchanged.
Setting parentId to null moves to root. The database derives the path and updates
descendant paths transactionally. Client-supplied paths, IDs, project IDs and
timestamps are rejected. Responses map the shared Category fields:
`id`, `projectId`, `name`, `parentId`, `path`, `sortOrder`, `createdAt`, `updatedAt`.

List parameters: `limit` (1–100, default 20), opaque `cursor`, and optional
`parentId=<uuid>` (direct children) or `parentId=root` (roots). No parent filter lists
all categories in the project. A missing/inaccessible parent filter returns 404.
Ordering is sortOrder then UUID, both ascending. Lists return
`{ data, pagination: { cursor, hasMore }, requestId }`; terminal cursor is null.
Cursors are validated and bound to the project and parent filter; reuse under a
different scope/filter returns 400. Pagination is not a snapshot: refresh after
concurrent moves or sort-order changes, which can move records across page boundaries.

Malformed IDs, bodies and cursors return 400 / `VALIDATION_ERROR`; missing or
inaccessible categories/parents return 404 / `NOT_FOUND`; insufficient roles return
403 / `FORBIDDEN`. Hierarchy check conflicts such as cycles return
409 / `CATEGORY_CONFLICT`. Deleting a category referenced by children or items
returns 409 / `CATEGORY_IN_USE` without cascading. Unexpected database failures
remain 500 / `INTERNAL_ERROR`. Every error uses the common envelope.

There is no recursive tree, batch reorder, category cascade-delete or frontend
endpoint in M5. Hosted setup must expose `inventory` alongside `control` while
keeping `private` unexposed; no hosted configuration has been changed locally.

## M6 Template builder backend

Base: `/api/v1/organisations/:orgId/projects/:projectId/templates`.
All project members may read; only project owner/admin (including inherited org
roles) may write. All storage access retains the caller JWT and inventory RLS.

| Method | Suffix | Behavior |
|--------|--------|----------|
| POST | `/` | Create metadata `{ name, description? }`; 201 |
| GET | `/` | Paginated metadata, createdAt/UUID ascending |
| GET | `/:templateId` | Read metadata/currentVersionId |
| PATCH | `/:templateId` | Edit name and/or nullable description |
| DELETE | `/:templateId` | Delete only if no retained versions |
| POST | `/:templateId/versions` | Create draft `{ schema }`; 201 |
| GET | `/:templateId/versions` | Paginated versions, number ascending |
| GET | `/:templateId/versions/:versionId` | Read draft/published version |
| PATCH | `/:templateId/versions/:versionId` | Replace draft `{ schema }` |
| DELETE | `/:templateId/versions/:versionId` | Delete draft only |
| POST | `/:templateId/versions/:versionId/publish` | No body; atomically publish and make current |

Names are trimmed 1–200 characters; descriptions are nullable, at most 2000
characters, default null on creation. PATCH requires a field. Unknown properties,
client tenant identity, timestamps, version numbers and current-version setters
are rejected. IDs must be UUIDs. Lists accept only limit (1–100, default 20) and
opaque cursor. Cursors bind to project and, for versions, template; they provide
ordered traversal, not a snapshot under concurrent changes. Timestamp cursors
preserve PostgreSQL precision.

Schemas are strict `{ fields: [...] }`. An empty array is allowed. Fields have
`key`, `label`, `type`, `required` (default false). Keys are unique and match
`^[a-z][a-z0-9_]{0,63}$`; prototype/constructor/__proto__ are forbidden. Labels are
trimmed, nonempty, at most 200 characters. Types: text, number, boolean, date,
select. Only select has `options`, a nonempty array of unique trimmed nonempty
strings, each at most 200 characters. Field/option order is retained. No defaults,
nesting, computed fields or custom constraints. This defines attribute metadata;
item-value validation belongs to M7.

Multiple drafts are allowed. Draft allocation locks the template and uses
max(existing version)+1; deleting the highest draft permits number reuse.
Publication validates the schema in PostgreSQL, sets a server timestamp and
updates currentVersionId in one transaction. Repeating publication returns 409;
publishing an older draft makes it current regardless of version number.
Published versions cannot be edited/deleted. Existing items keep their original
version; there is no automatic attribute migration or cascading deletion.
Historical schemas are returned unchanged, but invalid drafts must be replaced
before publication. TemplateVersion responses include projectId as well as id,
templateId, version, schema, publishedAt and createdAt.

Success uses `{ data, requestId }`; lists also include pagination. DELETE returns
`{ data: { id }, requestId }`. Common errors retain error/code/requestId:

| Status | Code | Condition |
|--------|------|-----------|
| 400 | VALIDATION_ERROR | Invalid input or cursor scope |
| 400 | INVALID_TEMPLATE_SCHEMA | Database publication/schema validation rejected input |
| 403 | FORBIDDEN | Insufficient role (including database RPC authorization) |
| 404 | TEMPLATE_NOT_FOUND | Absent/inaccessible template |
| 404 | TEMPLATE_VERSION_NOT_FOUND | Absent/inaccessible scoped version |
| 409 | TEMPLATE_IN_USE | Template retains versions/references |
| 409 | TEMPLATE_VERSION_PUBLISHED | Published version mutation or repeat publication |
| 409 | TEMPLATE_VERSION_CONFLICT | Version allocation collision/integer exhaustion |
| 500 | INTERNAL_ERROR | Unexpected/malformed database response |

Authentication/org/project middleware can return its existing 401/403/404 errors
before template lookup. Direct SQL published_at writes retain M4 permissions but
now require a valid typed schema; they do not implicitly set currentVersionId.
HTTP writes use the transactional publication RPC. Hosted PostgREST integration
and genuine concurrent database sessions remain unverified locally.

### Inventory items (M7)

Base: `/api/v1/organisations/:orgId/projects/:projectId/items`.
GET collection/single item requires project membership. POST, PATCH and DELETE
require project owner/admin/editor. Creation returns 201; other successes return
200. All responses include `requestId` and the common data envelope.

POST accepts `{ templateVersionId, name, categoryId?, sku?, attributes? }`.
Only a published template version in this project is accepted. Attribute keys,
required fields and values are checked against that immutable version's schema.
PATCH accepts name, categoryId, sku and attributes; attributes merge with stored
values before validation. At least one field is required. Template version and
quantity cannot be changed through item writes. Unknown fields are rejected.
DELETE returns `{ data: { id }, requestId }`; retained stock or attachment
references can prevent deletion. Retained stock/attachment references return
409 / `ITEM_IN_USE`.

List accepts limit, cursor, categoryId, templateId and search (name/SKU).
Ordering is createdAt descending, UUID ascending. Cursors bind project and
category/template filters. Search is not bound by the existing cursor format;
start a fresh listing when changing search. See OpenAPI for exact field bounds.

### Stock transactions (M8/M10)

Base: `/api/v1/organisations/:orgId/projects/:projectId/stock/movements`.
GET collection and `/:movementId` require project membership. POST requires
owner/admin/editor and returns 201. Movement history has no edit/delete endpoint.
POST accepts `{ itemId, type, quantity, reason?, referenceId? }`; quantity must be
positive and finite. Receive, return and adjust increase quantity; ship and
transfer decrease it. Transfer records an outbound movement only; it does not
credit a destination. Adjust currently supports increases only. A decrease uses
ship. No negative stock is permitted.

A locked database transaction writes the movement and item quantity together.
Migration 010 additionally checks JWT actor, project role and membership for
calls made directly through Supabase. Actor impersonation is forbidden. The RPC
lives in `inventory`, not `control`. Duplicate non-null referenceId values within
a project return 409 / `DUPLICATE_REFERENCE`; insufficient stock returns
409 / `INSUFFICIENT_STOCK`. These conflicts do not change quantity or history.
POST returns StockMovement fields plus `resultingQuantity`.

List accepts limit, cursor, itemId and type. Ordering is createdAt descending,
UUID ascending. Cursors bind project/item filters; start a fresh listing when
changing type. This is pagination, not a snapshot under concurrent writes.

### Attachments (M9)

Base: `/api/v1/organisations/:orgId/projects/:projectId/items/:itemId/attachments`.

| Method | Suffix | Access | Result |
|--------|--------|--------|--------|
| POST | `/` | Owner/admin/editor | 201, metadata reservation, bucket and path |
| GET | `/` | Project member | 200, paginated metadata reservations |
| GET | `/:attachmentId/download` | Project member | 200, `{ signedUrl }` |
| DELETE | `/:attachmentId` | Owner/admin/editor | 200, `{ id }` |

POST accepts only `{ filename }` (trimmed, 1–255 characters; no path separators or
control characters). Item must exist in the same project. Returned metadata uses
`id`, `project_id`, `item_id`, `filename`, `created_by`, `deleted`, `created_at`.
The reservation also returns `bucket: "inventory-attachments"` and a generated
`path` of `projectId/itemId/attachmentId`. Client IDs/actor/path are never accepted.

Upload bytes separately with the authenticated caller's Supabase client:
`supabase.storage.from(bucket).upload(path, file, { upsert: false })`.
Uploads require a current writer role and matching active metadata reservation.
This flow deliberately uses JWT-authenticated uploads, not upload bearer tokens.
Metadata listings include reservations whose bytes have not yet been uploaded;
a download before upload returns 404. No file type/size subscription quota is
invented. Configure Storage file restrictions explicitly for the deployment.

The bucket is private; objects cannot be overwritten through tenant policies.
Downloads force the stored filename and expire after 60 seconds. A previously
issued download URL remains usable until expiry, even after role revocation.
Deletion first tombstones metadata, denying subsequent new uploads/downloads,
then removes bytes through Storage API. Failed byte cleanup returns 500; retry
DELETE with the same ID. Tombstones remain for audit and cleanup retries and
retain the item. A concurrent in-flight upload can leave inaccessible bytes;
operators must reconcile orphan objects through Storage API, never SQL deletion.

List accepts limit (1–100, default 20) and UUID cursor, ordered UUID ascending.
Each query filters project/item and excludes tombstones. Cursors are positions,
not authorization capabilities; changing scope starts a new listing. UUID-order
pagination can miss concurrent inserts before the cursor.

### Audit and dashboard (M9)

GET `/api/v1/organisations/:orgId/projects/:projectId/audit` requires project
owner/admin. Returns paginated project audit events with `id`, `project_id`,
`actor_id` (nullable for maintenance), `action` (insert/update/delete),
`entity_type`, `entity_id`, `created_at`. Limit/cursor use the same UUID ordering
as attachments. This endpoint is project-scoped and distinct from existing
organisation-level `control.audit_logs`.

Database triggers record category, template, version, item, movement and attachment
metadata mutations in the same transaction. Events contain no attribute values,
credentials or object URLs. Failed transactions create no events. Tenant roles
cannot insert, edit or delete events. Storage byte uploads/downloads are not
metadata mutations and do not generate these events. Earlier records are not
backfilled. Project audit history retains project references.

GET `/api/v1/organisations/:orgId/projects/:projectId/dashboard` permits all project
members. Returns `{ data: { items, categories, templates, movements,
outOfStockItems }, requestId }`. Counts are computed in one caller-scoped SQL
statement; outOfStockItems counts quantity <= 0. The RPC lives in `public` and
returns null for inaccessible projects; HTTP scope middleware returns 404 first.
No valuation, low-stock threshold or cross-project aggregate is implied.

### Machine-readable contracts (M10)

GET `/api/v1/openapi.json` is public and returns OpenAPI 3.1. The checked-in copy
is `docs/openapi.json`. Generate with `npm run openapi --workspace packages/api`;
verify with `npm run openapi:check --workspace packages/api`.

Request schemas are shared with route validators. Successful wire responses are
validated against Zod contracts before return. Invalid successful responses yield
500 / `INTERNAL_ERROR`; internal details stay out of the response. Contract tests
verify method/path parity and formally validate OpenAPI with Swagger Parser.
Unknown routes use 404 / `NOT_FOUND` with the common JSON error envelope.
OpenAPI represents structural constraints; custom Zod refinements (non-empty
PATCH, unique field keys/options, attribute typing and cursor scope) also apply.
No API-managed sign-in or refresh endpoint exists; use Supabase Auth.
